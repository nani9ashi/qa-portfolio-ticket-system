## 1. 目的

本書は、**「どのテストを・どの層で・なぜ検証するのか」** という判断を明文化する。本拡張で新設した runn による **API/インテグレーションテスト層** の根拠と、既存 E2E（Playwright）との責務分担（再配分）を、後から検証可能な形で残すことが目的である。

## 2. 背景：なぜこの層を足すのか

このアプリの品質リスクの中心は **RBAC（認可）と状態遷移** にある。これらは本質的に **組合せが爆発** する。

- **認可マトリクス**：アクター（管理者／担当Agent／非担当Agent／所有Requester／非所有Requester／未認証）× 操作（一覧・詳細・作成・状態変更・担当変更・期限変更・コメント）× リソース所有（自分／他人）。
- **状態遷移**：状態（5）× 遷移先（妥当/不当）× ロール制約（R1-R6）。

この組合せを **E2E（ブラウザ）で網羅すると、遅く・脆い**。

- **遅い**：1ケースごとに Chromium 起動・画面遷移・DOM 安定待ちが要る（実測：4シナリオで数秒だが、これを数十〜百ケースに広げると分単位）。
- **脆い**：セレクタ・画面レイアウト・描画タイミングに依存し、**業務ロジックと無関係な理由で壊れる**。
- **観測点が粗い**：UI 経由では「禁止された操作」を送ること自体が難しく（ボタンが出ない＝そもそも押せない）、サーバ側の拒否ロジックを直接突けない。既存 Auto-04 が「直叩き POST は CSRF 処理コストにより自動化スコープ外」としていたのはこの典型。

一方、これらのロジックは **入力に対して期待結果が一意に決まる決定的な世界** にある。だからこそ、**速く・決定的に叩ける下層（API/インテグレーション）へ押し下げる** のが正しい。E2E は「端から端まで本当に繋がっているか」を示す代表シナリオに絞る。

## 3. 判断：どのテストを・どの層で

| レイヤ | 担うもの | 規模 | 根拠 |
|---|---|---|---|
| **手動 TC** | 仕様の深掘り・探索的・ユーザビリティ | 46件 | 人間が見るべき領域 |
| **API/runn（新設）** | 認可マトリクス・IDOR・状態遷移（妥当/不当/ロール制約）・入力境界値 の **組合せ網羅** | **10 runbook / 102 ステップ** | 決定的・高速・観測点が細かい |
| **E2E/Playwright（再配分）** | 代表的ユーザー導線（ハッピーパス）＋ 認可スモーク ＋ UI 抑止 ＋ 実欠陥回帰 | 4シナリオ | フルスタックで繋がることの担保 |

runn 層の内訳（[API README](../api/README.md)）：(a) 認可+IDOR=5 runbook / 43 step、(b) 状態遷移=3 runbook / 43 step、(c) 入力検証=2 runbook / 16 step。

## 4. 期待値の写像（① の決定的な世界の体現）

新 API は**新規コード**なので、同じ業務 **ルール** を **意味的に正しい HTTP ステータス** で表現する。これにより期待値が一意に書き下せる（これが本拡張の知的な核であり、§7 の②との対比点でもある）。

| 結果 | 現 HTML | API | 意図 |
|---|---|---|---|
| 読取/更新 成功 | 200 / 302 redirect | **200**（作成は **201**） | API はリソースを返す |
| 未認証 | 302→login | **401** | Token 認証（未認証は一意に 401） |
| 認可拒否（ロール/所有/**IDOR**） | 403 | **403** | IDOR も忠実にミラー（存在露見も実挙動どおり） |
| 不正ステータス値（enum 外） | 403 `"invalid"` | **400** | 入力不正 |
| 不正遷移（enum 内・禁止エッジ） | 403 `"invalid transition"` | **409 Conflict** | 状態競合 |
| 非 Agent を assignee 指定 | 403 | **400** | 業務入力検証 |
| 文字数超過 / 過去日 | 200 再描画 / **500（DEFECT-003）** | **400** | 検証エラー |
| 不在 pk | 404 | **404** | ミラー |

> HTML が「拒否はすべて 403 文言」で表すのに対し、API は **401/403/400/409/404** に分けて書ける。**期待値表が一意に書けること自体**が、この層を成立させている。

## 5. 単一ソース・オブ・トゥルース（整合性の担保）

API が HTML と **別のロジックを再実装** してしまっては、「テストが本物を見ている」保証が崩れる。そこで認可・状態遷移の判定を [app/tickets/policy.py](../../app/tickets/policy.py) に **一本化** し、HTML ビューと API の **両方が同じ述語を呼ぶ**。

- 検証：`settings.INTENTIONAL_BUG_IDOR=True` にすると、共有する `policy.can_view` が両経路で同時に破綻し、**API の IDOR テスト（`rbac_idor/idor.yml`）と E2E の Auto-02 が、同一原因で同時に失敗** する。「1スイッチで両層が落ちる」ことが、両者が同じ対象を見ている証拠である。
- 入力検証も同様に、モデルの `full_clean()`（`Ticket.clean()` / `MaxLengthValidator`）を両層が共有する。

このリファクタは「テスト容易性のための最小限の構造分離」であり、プロダクト機能の追加ではない（[ナラティブ制約](../../README.md)を遵守）。

## 6. E2E 再配分（before / after）

| シナリオ | before | 判断 | after |
|---|---|---|---|
| **Auto-01** ハッピーパス（作成→詳細） | E2E | **KEEP** | E2E（代表導線） |
| **Auto-02** IDOR 回帰 | E2E | **KEEP（認可スモーク1本）** | E2E（組合せ IDOR は `rbac_idor/` へ拡張） |
| **Auto-03** 本文4001境界 | E2E | **MOVE → API** | API層へ移設し削除（`validation/title_body_boundary.yml`） |
| **Auto-04** 非担当Agent UI抑止 | E2E（UI＋スコープ外注記） | **KEEP（UIのみへ限定）** | E2E（サーバ側認可は `transitions/role_constraints.yml` R4 へ） |
| **Auto-05** 期限過去日の graceful 拒否 | （無） | **ADD** | E2E（DEFECT-003 の HTML 回帰。API 期待値=400 は `validation/due_date.yml`） |

結果：**組合せ網羅（RBAC×状態×境界）は API 層へ移り**、E2E はハッピーパス＋認可スモーク＋UI 抑止＋実欠陥回帰の4本に収束した。Auto-03 が担っていた境界値は API 層で **4点境界（空/1/max/max+1）** に拡張されている。

## 7. ② への布石（決定的な世界という土台）

本 API 層が成立するのは、**入力に対して期待レスポンスが一意に定まる「決定的な世界」** だからである。状態遷移表・権限マトリクス・境界値という形で、**期待値を厳密に書き下せる**。

この「**期待値を厳密に書き下せること自体**」が、次作 **②（生成 AI プロダクトの QA）** との対比点になる。②では出力が確率的に揺らぎ、**そもそも期待値表が書けない**。だからこそ ②は LLM-as-a-judge 等の別アプローチが要る。①は「型を正しく実行する決定的な世界」を担当する基礎編であり、本層はその体現である。

## 8. 残った問い（別方向の宿題）：コンシューマ駆動契約テスト（CDC）

本層は **単一サービス内** の統合点（HTTP API）を検証する。もし将来 **サービスが複数に分割され独立デプロイ** されるようになったら、この統合点（API 契約）を「提供側と消費側がそれぞれ独立に・契約として」守る必要が出る ＝ **コンシューマ駆動契約テスト（CDC, 例：Pact）** の領域である。

- 現状は単一サービスのため **実装しない**。本書に「次の層の問い」として記録するに留める。
- ※これは ①→② を繋ぐ主問題（**「このテスト自体が間違っていたら、誰が気づくのか？」**）とは **別方向** の宿題であり、連作の背骨とは競合させない。

## 9. スコープ外・既知の限界（誠実さ）

- **CDC/Pact は未実装**（§8、README の「残った問い」として記録のみ）。
- **添付（attachment）の境界**（拡張子・5MB）は API create の対象外とした。組合せ価値（RBAC×状態と乗算しない単一軸）が薄く、multipart を runn に持ち込む費用に見合わないため。境界は E2E/手動（TC-038/039）に残す。
- **期限の「当日ちょうど」境界** は、CI を日付非依存に保つため runn では明確な過去/未来日で検証している（当日が valid であることはルール上自明：`< 当日` のみ不可）。
- **API のステータスコードは HTML と意図的に異なる**（§4）。これは「同じルールを別の表現で検証している」ことの明示であり、対応表で追跡可能にしている。
