## 1. 目的

「**どのテストを・どの層で・なぜ検証するのか**」を明文化する。本アプリの自動テストは **単体（pytest）／ API・インテグレーション（runn）／ E2E（Playwright）** の3層からなる。各層の責務と、その配分の根拠を、後から検証可能な形で残す。

## 2. なぜ層で分けるのか

本アプリの品質リスクの中心は **認可（RBAC）と状態遷移** にあり、これらは本質的に **組合せが爆発** する。

- **認可**：アクター（Admin／担当Agent／非担当Agent／所有Requester／非所有Requester／未認証）× 操作 × リソース所有（自分／他人）。
- **状態遷移**：状態（5）× 遷移先（妥当／不当）× ロール制約。

この組合せを **E2E（ブラウザ）で網羅すると、遅く・脆く・観測点が粗い**。1ケースごとにブラウザ起動と描画待ちが要り、セレクタや描画タイミングという **業務ロジックと無関係な理由で壊れ**、UI 経由では「禁止された操作」を送ること自体が難しい（ボタンが出ない＝押せない）。

一方これらのロジックは、**入力に対して期待結果が一意に決まる決定的な世界** にある。だから **速く・決定的に叩ける下層へ押し下げる** のが正しい。純ロジックは単体へ、HTTP 契約は API へ。E2E は「端から端まで本当に繋がっているか」を示す代表シナリオに絞る。

## 3. 層の分担

| レイヤ | 担うもの | 規模 | 速度・根拠 |
|---|---|---|---|
| **単体 / pytest（新設）** | `policy.py` の純ロジック：認可述語（`can_assign` / `can_view` / `can_update_status` / `can_create` / `can_change_due`）と状態遷移（`can_transition_to` / `check_status_change`） | **53件 / policy.py 100%** | 最速・最安（ブラウザもサーバも不要、48件が約0.4秒）。状態遷移は5×5全網羅、認可はロール×所有を網羅 |
| **API / runn** | 認可マトリクス・IDOR・状態遷移・入力境界値の **組合せ網羅**（HTTP 契約として） | 10 runbook / 102 step | 決定的・高速・観測点が細かい |
| **E2E / Playwright** | 代表導線（ハッピーパス）＋ 認可スモーク ＋ UI 抑止 ＋ 実欠陥回帰 | 4シナリオ | フルスタックで繋がることの担保 |
| **手動 TC** | 仕様の深掘り・探索的・ユーザビリティ | 46件 | 人間が見るべき領域 |

**単体層の設計方針（カバレッジは床、mutation が担保）**：policy.py はカバレッジ **100%**。ただし **カバレッジは「床」であって「正しさの証明」ではない**——全行を踏んでいても、テストが結果を検証していなければバグは見逃される（緑＝正しい、ではない）。本層の真の担保は **変異（mutation）テスト**：認可・状態遷移のロジックを意図的に壊すと、対応するテストが必ず失敗することを確認している。**カバレッジで未到達の穴を見つけ、mutation で検出力を確かめる**、の二段構えを取る。

## 4. API 期待値

API は新規コードなので、同じ業務ルールを **意味的に正しい HTTP ステータス** で表現する。これにより期待値が一意に書き下せる。

| 結果 | 現 HTML | API | 意図 |
|---|---|---|---|
| 読取／更新 成功 | 200 / 302 redirect | **200**（作成は **201**） | API はリソースを返す |
| 未認証 | 302→login | **401** | Token 認証（未認証は一意に 401） |
| 認可拒否（ロール／所有／**IDOR**） | 403 | **403** | IDOR も忠実にミラー |
| 不正ステータス値（enum 外） | 403 `"invalid"` | **400** | 入力不正 |
| 不正遷移（enum 内・禁止エッジ） | 403 `"invalid transition"` | **409 Conflict** | 状態競合 |
| 非 Agent を assignee 指定 | 403 | **400** | 業務入力検証 |
| 文字数超過／過去日 | 200 再描画 / **500（DEFECT-003）** | **400** | 検証エラー |
| 不在 pk | 404 | **404** | ミラー |

> HTML が「拒否はすべて 403 文言」で表すのに対し、API は **401 / 403 / 400 / 409 / 404** に分けて書ける。**期待値表が一意に書けること自体** が、この層を成立させている。

## 5. 単一ソース・オブ・トゥルース

各層が別々のロジックを再実装しては、「テストが本物を見ている」保証が崩れる。そこで認可・状態遷移の判定を [`app/tickets/policy.py`](../../app/tickets/policy.py) に **一本化** し、**単体・API・E2E の3層すべてが、同じ述語を検証する**。

- **証拠**：`settings.INTENTIONAL_BUG_IDOR = True` にすると、共有する `policy.can_view` が破綻し、**単体の IDOR テスト・API の `rbac_idor/idor.yml`・E2E の Auto-02 が、同一原因で同時に失敗** する。1つのスイッチで3層が落ちることが、3層が同じ対象を見ている証拠である。
- 入力検証も同様に、モデルの `full_clean()`（`Ticket.clean()` / `MaxLengthValidator`）を各層が共有する。

このリファクタは「テスト容易性のための最小限の構造分離」であり、プロダクト機能の追加ではない。

## 6. E2E 再配分（before / after）

| シナリオ | before | 判断 | after |
|---|---|---|---|
| **Auto-01** ハッピーパス（作成→詳細） | E2E | **KEEP** | E2E（代表導線） |
| **Auto-02** IDOR 回帰 | E2E | **KEEP（認可スモーク1本）** | E2E（組合せ IDOR は `rbac_idor/` へ拡張） |
| **Auto-03** 本文4001境界 | E2E | **MOVE → 下層** | API `validation/title_body_boundary.yml`（4点境界）＋単体へ移設し削除 |
| **Auto-04** 非担当Agent UI抑止 | E2E（UI＋スコープ外注記） | **KEEP（UI のみへ限定）** | E2E（サーバ側認可は API `role_constraints.yml` R4 と単体 `can_update_status` へ） |
| **Auto-05** 期限過去日の graceful 拒否 | （無） | **ADD** | E2E（DEFECT-003 の HTML 回帰。API 期待値=400 は `validation/due_date.yml`） |

結果：**組合せ網羅（RBAC × 状態 × 境界）は下層（単体・API）へ移り**、E2E はハッピーパス＋認可スモーク＋UI 抑止＋実欠陥回帰の4本に収束した。

## 7. スコープ外

- **添付（attachment）の境界**（拡張子・5MB）：組合せ価値が薄く（単一軸で RBAC×状態と乗算しない）、multipart を runn に持ち込む費用に見合わないため、E2E／手動（TC-038/039）に残す。
- **コンシューマ駆動契約テスト（CDC / Pact）**：本アプリは単一サービスのため **未実装**。将来サービスが分割・独立デプロイされた場合に、API 契約を提供側・消費側が独立に守る手段として検討対象になる。現状は「次の層の問い」として記録に留める。
- **API のステータスコードは HTML と意図的に異なる**（§4）：同じルールを別表現で検証していることの明示であり、対応表で追跡可能にしている。

---

本層が扱うのは「入力に対して期待が一意に定まる **決定的な世界**」である。この確実性は、出力が確率的に揺らぐ生成 AI プロダクトの QA（ポートフォリオ②）では成り立たず、別アプローチ（LLM-as-a-judge 等）を要する——本作はその対比の基礎編に当たる。
